# R49末段归零原因与R47、R48fix1对比

## 结论

R49在00:29:30和00:30:00的严格AR产品归零，直接原因是最终产品整数账本的联合精确一致性检查拒绝提交，随后整个PRODUCT_FIXED批次被删除，整数账本与规范证书账本恢复到搜索前快照。不是程序崩溃，也不是该历元没有搜索出任何认证关系。

已确认的是“账本联合检查拒绝 → 发布授权撤销 → 整批产品和暂存协方差不提交 → 账本回滚”。尚未确认的是构成冲突的最小关系集合、相关卫星/弧段、当前解与历史解哪一方错误，以及究竟触发有理仿射矛盾还是整数格可行性失败。日志将两类失败合并为同一个错误码。

## 代码机制

代码依据为本次实际运行的冻结源代码：`/home/rx/GINAN/frozen-r49-condition-domain-20260913/source`，对应二进制源提交793814c。

1. `src/cpp/common/zhangProductIntegerLedger.hpp:510`附近先复制既有账本为`proposedRows`，然后处理当前候选。约638—658行把proposedRows中的全部`physicalExpansionExact`关系放入精确联合系统F*N=n。这里的检查范围包含既有账本关系，不限于当前搜索选中的历史条件行。
2. 649行进行精确行Hermite标准形的一致性检查，656行检查n是否属于F的列整数格。658—662行中任一条件失败，都返回同一错误码`PRODUCT_LEDGER_TRUE_PHYSICAL_AFFINE_CONFLICT`，不把候选副本提交到账本。
3. `src/cpp/pea/zhangPppAr.cpp:11630`附近撤销当前系统所有PRODUCT_FIXED产品的整数有效标志。11670—11672行在原子提交不成立时，直接删除epochProducts中的全部PRODUCT_FIXED记录；其暂存协方差同样不写出。
4. `src/cpp/pea/ppp_ambres.cpp:31250`附近在产品事务未提交时，恢复搜索前的整数账本和规范证书账本。

所以，“前面某些候选通过NIS/形成连通分量”并不保证“这些候选与全部持久账本能组成同一整数解”。当前发布事务没有在此失败分支上执行局部冲突隔离、对未受影响分量重新认证后再提交。这使联合冲突在输出上表现为整批停供。拒绝不一致关系是必要保护；改进应针对冲突定位和独立安全子集重建，不能直接放行冲突或照搬旧产品。

00:30:00再次失败与账本回滚后的重复冲突现象一致，但现有日志无法证明两次是完全相同的最小冲突集合。

## 为什么最终检查仍然PASS

本次PEA退出0、runner退出0，61个产品CSV历元和61个检查点齐全，既有数值告警扫描无命中。`verify_r49.py:56`的告警列表不包括上述PRODUCT_LEDGER错误码；它会统计产品归零，但没有把首次出产品后的归零设为runtime_pass失败条件。最后两个历元仍有FLOAT、NETWORK_WL和NETWORK_FIXED_DIAGNOSTIC记录，因此普通产品CSV历元覆盖检查仍然通过。

这说明当前PASS是运行完成及已列数值检查通过，不能用作稳定AR服务验收。今后宜分别输出runtime_pass、publication_integrity和service_continuity指标，明确记录末段停供，而不是把安全拒绝错误地等同于程序崩溃。
